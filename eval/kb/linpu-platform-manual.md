# linpu（林谱）智能体平台技术手册

文档编号：LP-TECH-2026-011
适用版本：linpu v2.4.0
最后更新：2026-11-10

## 1 文档说明与核心结论

本手册是 linpu（林谱）智能体平台的内部技术手册，覆盖架构、部署、接口、运维与规范。

本文档的核心结论是：linpu 平台采用「一个 Java 单体 + 两个 Python 微服务」的混合架构，业务与权限数据存放在 MySQL，向量检索数据存放在启用 pgvector 扩展的 PostgreSQL，缓存与限流计数存放在 Redis。平台对外只暴露一个网关端口，内部服务之间通过 gRPC 与 HTTP 通信。

## 2 系统架构

平台分为四层。

第一层是接入层，由 Nginx 承担静态资源分发与反向代理，对外监听 80 端口，将 `/prod-api/` 前缀的请求转发给后端网关 18080 端口。

第二层是应用层，核心是 linpu-admin 单体服务，承载权限、菜单、字典、日志、定时任务等后台能力，同时承载 AI 业务的主流程编排。

第三层是智能体服务层，包含两个独立进程：agentic 智能体编排服务监听 18142 端口，负责大模型调用、工具执行、多智能体流程编排；doc-parser 文档解析服务监听 18143 端口，负责把 PDF、Word、Excel、PPT 等格式转换为 Markdown 文本。

第四层是数据层，MySQL 8.0 监听 3306，Redis 监听 6379，PostgreSQL 15 配合 pgvector 监听 5432。向量维度固定为 768 维，与本地向量模型 text2vec-base-chinese 的输出维度一致。

## 3 关键流程步骤

一次完整的知识库问答分为六步。

第一步，客户端提交问题，网关鉴权后进入对话控制器。

第二步，控制器读取智能体配置，取得绑定的知识库编号、系统提示词与模型编号。

第三步，使用默认向量模型把问题编码为 768 维向量。

第四步，在 pgvector 中按余弦距离检索，召回条数由智能体的 max_result 字段控制，默认值为 5 条，相似度阈值由 min_score 控制，默认值为 0.7。

第五步，把召回的分段文本拼接进提示词模板，模板中的占位符是 `{question}`，替换为原始问题后提交给大模型。

第六步，大模型以流式方式返回，服务端通过 SSE 逐块推送给前端，事件类型包括 text、tool_call、tool_called、error。

## 4 主要风险点

第一个风险是文档解析服务的模型加载。doc-parser 启动时需要加载 OCR 模型，若采用启动期同步下载，会导致启动阻塞数分钟并且在网络抖动时直接启动失败。当前版本已改为懒加载，仅在首次处理 PDF 时加载。

第二个风险是模型配置的缓存一致性。大模型与向量模型的实例会被缓存以降低重建开销，因此修改模型配置后必须使缓存失效，否则会继续使用旧连接。

第三个风险是长连接中断。agentic 与后端之间的 gRPC 长连接在空闲后可能被中间设备断开，需要在客户端侧实现 keepalive 心跳与服务不可用时的自动重连。

第四个风险是流式输出的并发压力。SSE 会话数量上升后连接与内存占用会线性增长，需要做会话级并发限制。

## 5 部署说明

部署采用 Docker Compose 编排，共九个容器：nginx、linpu-admin、agentic、agentic-sandbox、doc-parser、mysql、redis、pgvector，以及可选的 dify 组件。

部署的要点有三个。第一，构建镜像时必须清除宿主环境注入的 HTTP_PROXY 变量，否则容器内访问软件源会失败。第二，Windows 环境下检出的 Shell 脚本可能带 CRLF 换行，需要在 Dockerfile 中做行尾归一化，否则容器内 dash 执行会报非法选项。第三，向量模型文件建议通过卷挂载持久化，避免容器重建后重复下载约 1.8 GB 的模型文件。

部署完成后的验收顺序是：先确认 MySQL 与 PostgreSQL 健康检查通过，再确认 vector 维度检查接口返回成功，最后确认网关首页返回 200。

## 6 数据安全说明

平台对敏感数据采取三项措施。

其一，数据库中的 API Key 字段仅在服务端使用，接口返回时做掩码处理。

其二，客户端上传的文档存放于挂载卷中，不进入版本库，且 `.env` 文件被版本控制忽略。

其三，所有涉及写操作的接口都要求具备对应权限标识，权限标识的命名规则是 `ai:模块名:操作`。

此外，应用日志不得记录完整的 API Key 与用户密码，违反者按三级事故处理。

## 7 功能输入输出

以「文档向量化」能力为例。

输入包含四个必需项：知识库编号 kbId、向量模型编号 embeddingModelId、文件列表 fileList，以及分段参数 maxSegmentSize 与 maxOverlapSize。

输出分为两部分：同步返回分段数量与批处理大小，异步通过 WebSocket 推送向量化完成通知。

分段默认长度 500 字符，重叠 50 字符。批处理大小由参数 `ai.embedding.batchSize` 控制，默认值为 5。

## 8 性能指标要求

平台对性能的硬性要求如下。

网关接口的 P95 响应时间不得超过 800 毫秒（不含大模型生成时间）。

大模型对话的首 Token 延迟 P50 不得超过 1500 毫秒。

流式输出的完整率不得低于 99.5%，即每千次会话中截断次数不超过 5 次。

知识库检索环节的 P95 延迟不得超过 300 毫秒。

系统需支持 200 个并发在线会话，单实例内存占用不超过 4 GB。

## 9 第三章内容概括

手册第三章的标题是「关键流程步骤」，内容是知识库问答的六个执行步骤，重点说明了检索召回的两个可调参数 max_result 与 min_score 的默认取值，以及 SSE 推送的四种事件类型。第三章还强调了提示词模板中 `{question}` 占位符的替换时机是在检索完成之后。

## 10 主要技术选型

后端语言为 Java 17，框架为 Spring Boot 2.5.x，权限体系沿用经典的 RBAC 模型。

AI 编排框架为 LangChain4j，向量数据库为 PostgreSQL 15 加 pgvector 扩展。

前端为 Vue 2 加 Element UI，构建工具为 Webpack 4。

智能体服务使用 Python 3.11 加 FastAPI，文档解析使用 Docling 与 RapidOCR。

容器编排使用 Docker Compose，数据库迁移使用 Flyway。

## 11 接口调用方式

以对话接口为例。

请求方式为 POST，路径为 `/ai-chat`，请求体为 JSON，关键字段包括 agentId（智能体编号）、prompt（用户问题）、clientId（客户端标识）、sessionId（会话标识）。

响应类型为 `text/event-stream`，即 SSE 流式响应。

该接口在安全配置中属于免登录白名单，但每个客户端受每日调用次数限制。

## 12 配置项说明

平台的关键配置项如下。

`ai.model.embedding` 指定默认向量模型的编号。

`ai.embedding.batchSize` 指定向量化的批处理大小，默认为 5。

`ai.agent.sessionNum` 指定会话记忆保留轮数，默认为 10。

`ai.model.saveDir` 指定本地模型文件的保存目录，默认为 `./models`。

`ai.pgvector.dimension` 指定向量维度，必须为 768，与向量模型输出保持一致。

`sys.account.captchaEnabled` 控制登录验证码开关，生产环境必须为 true。

## 13 限制条件

单个文档的大小上限为 50 MB。

单次向量化的分段数量上限为 2000 段。

模型输入的上下文长度上限为 8192 tokens，超出部分会被截断。

单次对话的连续工具调用轮数上限为 5 轮。

知识库数量上限为 100 个，单个知识库挂载的智能体数量不设上限。

## 14 模块职责边界

linpu-admin 负责权限、配置、业务编排与对外接口，不直接持有模型实例的构建逻辑。

agentic 只负责智能体执行，不负责用户鉴权与权限判断。

doc-parser 只做格式转换与文本抽取，不做分段与向量化。

agentic-sandbox 只提供代码执行沙箱，不承载业务逻辑。

数据库迁移由 linpu-admin 通过 Flyway 独占执行，其他服务不得执行 DDL。

## 15 错误码定义

平台错误码格式为 `LP-四位数字`。

LP-4001 表示参数校验失败。

LP-4002 表示鉴权失败或令牌过期。

LP-4003 表示权限不足。

LP-4004 表示资源不存在。

LP-4005 表示模型调用失败。

LP-4006 表示向量维度不匹配。

LP-4007 表示超出调用限额。

LP-4008 表示文档解析失败。

LP-4009 表示下游服务不可用。

## 16 参数可选值说明

`provider` 字段的可选值为三个：`Ollama`、`Open AI`、`local`，注意 `Open AI` 中间包含一个空格，是枚举的字面值。

`type` 字段的可选值为两个：`0` 表示大语言模型，`1` 表示向量模型。

`status` 字段在智能体上可取三个值：`0` 未启用、`1` 已启用、`2` 已停用。

`agent_type` 字段的可选值为 `origin`（原生智能体）、`dify`（Dify 智能体）、`flow`（流程编排智能体）。

## 17 版本兼容性

linpu v2.4.0 兼容 v2.2 及以上的数据库结构，升级时通过 Flyway 自动迁移。

v2.4.0 不再兼容 v2.0 及更早版本的向量维度，旧版本的 512 维向量需要在升级后重新向量化。

前端最低要求 Node.js 16，推荐 Node.js 18。Webpack 4 无法解析 ESM 语法的依赖包，因此 markdown-it 必须锁定在 13.x 版本。

## 18 适用场景

平台适用于三类场景。

第一类是企业内部知识问答，把产品文档、制度文件、技术手册灌入知识库后提供检索问答。

第二类是业务流程自动化，通过多智能体流程编排把多个智能体串成流水线。

第三类是代码与数据处理辅助，通过沙箱工具执行 Python 代码完成数据清洗与计算。

不适用的场景是超低延迟的实时推理（要求首 Token 低于 300 毫秒）以及离线批量推理。

## 19 降级策略

平台定义三级降级。

一级降级：向量检索超时，跳过检索直接使用大模型自有知识回答，并在响应中标注「未使用知识库」。

二级降级：大模型主通道失败，切换到备用通道，备用通道由配置项指定。

三级降级：下游服务完全不可用，返回错误码 LP-4009 并提示用户稍后重试。

降级由熔断器触发，熔断阈值为连续 10 次失败，熔断持续时间为 60 秒。

## 20 整体数据流

数据从上传开始流动：客户端上传文件到网关，网关写入挂载卷，记录文件路径到元数据。

随后文档解析服务把文件转为 Markdown，分段服务按 500 字符切分。

向量模型把每段编码为 768 维向量，连同元数据写入 pgvector，元数据中的关键字段是 kb_id。

对话时，问题向量化后在 pgvector 中检索，召回结果按相似度倒序拼入提示词。

大模型的输出经 SSE 推送前端，同时写入会话表与调用记录表，供审计与统计使用。

## 21 日志规范

日志级别分为 ERROR、WARN、INFO、DEBUG 四级，生产环境默认 INFO。

异常日志必须携带完整堆栈，Python 侧使用 `logger.exception` 或 `exc_info=True`，禁止只记录异常消息字符串。

单条日志不得包含密码、完整 API Key、身份证号等敏感信息。

日志格式要求包含时间、级别、线程、类名、追踪号 traceId 五个要素。

日志文件按天切分，单个文件上限 100 MB，最多保留 30 个文件。

## 22 指标统计口径

「会话数」按 sessionId 去重统计，同一会话内多轮问答只计一次。

「调用次数」按请求计数，每次请求计一次，包含命中限流而被拒绝的请求。

「首 Token 延迟」从请求到达网关开始计时，到大模型返回第一个非空文本块为止。

「完整率」等于完整结束的会话数除以总会话数，被用户主动中断的会话不计入分母。

「召回命中率」指答案中包含召回分段中关键短语的比例。

## 23 术语定义

「分段」（segment）：文档切分后的最小检索单元，默认 500 字符。

「召回」（retrieve）：从向量库中按相似度取出若干分段的过程。

「智能体」（agent）：绑定模型、提示词与工具的执行单元。

「技能」（skill）：以 Markdown 描述的提示词片段，可挂载到智能体上。

「工具」（tool）：智能体可以调用的函数，分内置工具与沙箱工具两类。

「编排」（flow）：把多个智能体按树形结构串接的执行图。

## 24 流程触发条件

知识库检索的触发条件是智能体的 kb_ids 字段非空。

工具调用的触发条件是大模型在响应中返回了工具调用意图，且该工具已挂载到当前智能体。

流程编排的触发条件是请求命中 flow 类型的智能体。

向量化的触发条件是运维或业务人员在知识库页面主动点击向量化，或通过接口调用。

会话记忆压缩的触发条件是历史消息轮数超过配置项 `ai.agent.sessionNum`。

## 25 限流策略

限流分两个维度。

客户端维度：每个客户端每天最多 1000 次对话调用，计数键为「智能体编号 + 客户端标识」，计数器在 Redis 中按天过期。

会话维度：单个客户端同时进行的流式会话不超过 3 个，超出返回 LP-4007。

接口维度：登录接口同一 IP 每分钟最多 10 次。

限流算法的实现基于 Redis 的 Lua 脚本，保证计数与过期判断的原子性。

## 26 监控项

必须监控的指标有八项：服务存活状态、HTTP 错误率、P95 响应时间、SSE 活跃连接数、向量检索延迟、大模型调用成功率、Redis 内存使用率、数据库连接池占用率。

告警阈值：HTTP 5xx 错误率超过 1% 持续 5 分钟；P95 响应时间超过 2 秒持续 5 分钟；活跃连接数超过 200。

## 27 备份与恢复

MySQL 每日 03:00 执行全量逻辑备份，保留 7 份，备份文件加密后存放于独立存储。

PostgreSQL 每日 03:30 执行全量备份，同时保留 WAL 归档以支持时间点恢复。

Redis 仅作为缓存与计数，不做持久化备份，重启后计数重置。

恢复演练每季度一次，恢复目标 RPO 为 24 小时，RTO 为 2 小时。

## 28 外部服务依赖

平台依赖三类外部服务。

第一类是大模型推理服务，通过 OpenAI 兼容协议访问，由 base_url 与 api_key 配置。

第二类是模型文件仓库，用于下载开源的向量模型与 OCR 模型。

第三类是可选联网搜索服务，用于给智能体补充实时信息，未配置时该能力自动关闭。

任何外部服务不可用都不得导致主流程崩溃，必须有超时与降级。

## 29 异常成因分析

LP-4006 向量维度不匹配的常见成因是更换了向量模型但未重新向量化，或配置的维度与实际模型输出不一致。

LP-4008 文档解析失败的常见成因是文件损坏、加密 PDF、或解析服务未加载完成。

LP-4009 下游不可用的常见成因是容器未启动、健康检查失败、或长连接被中间设备断开后未重连。

LP-4005 模型调用失败的常见成因是 API Key 失效、余额不足、或请求体超出上下文长度。

## 30 功能配置步骤

配置一个可用的知识库问答需要五步。

第一步，在模型管理中确认存在一个向量模型，并将其设为默认向量模型。

第二步，新建知识库，记录知识库编号。

第三步，上传文档并执行向量化，确认分段数量大于零。

第四步，新建智能体，绑定大模型，填写系统提示词，填写知识库编号 kb_ids。

第五步，把智能体状态改为已启用，然后通过访问链接进入对话页验证。

## 31 权限控制

权限模型基于 RBAC，用户关联角色，角色关联菜单与按钮权限。

AI 相关权限标识统一以 `ai:` 开头，例如 `ai:model:list`、`ai:knowledgeBase:add`、`ai:agent:edit`。

数据权限按部门隔离，可通过角色配置为全部数据权限或本部门数据权限。

超级管理员拥有 `*:*:*` 通配权限，生产环境应限制其账号的使用范围。

## 32 字段含义与取值范围

`min_score`：检索相似度阈值，取值范围 0 到 1，默认 0.7，值越大召回越严格。

`max_result`：单次召回条数，取值范围 1 到 20，默认 5。

`memory_count`：会话记忆轮数，取值范围 1 到 50，默认 3。

`temperature`：模型温度，取值范围 0 到 2，默认 0.7。

`day_lmt_per_client`：客户端每日调用上限，取值范围 1 到 100000，默认 1000。

## 33 测试策略

测试分四层。

单元测试覆盖纯逻辑模块，例如流程树解析器与 SSE 格式化器，要求行覆盖率不低于 60%。

接口测试覆盖核心业务接口，使用脚本化批量调用并断言返回结构。

端到端评测使用固定评测集，按维度统计准确率、延迟与稳定性。

回归测试在每次发布前执行，任一 P0 用例从通过变为失败即阻断发布。

## 34 部署拓扑

生产环境采用单机多容器拓扑：一台 8 核 16 GB 的宿主机运行全部容器。

接入层的 Nginx 直接占用 80 端口，应用层的 linpu-admin 不直接对外暴露。

数据层三个容器共享同一台宿主机，通过 Docker 内部网络通信，不对宿主机暴露端口。

如需要高可用，可把数据层拆到独立宿主机，并对 linpu-admin 做双实例加负载均衡，但需注意会话状态存放在 Redis 中。

## 35 推荐做法

推荐把系统提示词写得具体，明确角色、输出格式与拒答边界。

推荐把知识库按主题拆分，而不是把所有文档塞进同一个知识库。

推荐 min_score 设在 0.7 附近，过低会引入噪声，过高会漏召回。

推荐生产环境关闭验证码以外的调试开关，并把日志级别设为 INFO。

推荐定期清理会话表与调用记录表，避免单表数据量过大影响查询。

## 36 数据保留周期

会话消息保留 90 天，超期归档后删除。

工具调用记录保留 180 天。

登录日志保留 180 天。

操作日志保留 365 天。

向量数据随文档删除而删除，文档删除后需手动触发重新向量化以同步清理。

备份文件保留 7 份，超出后按时间先后滚替。

## 37 扩容说明

垂直扩容优先：先提升宿主机内存与 CPU，成本最低。

水平扩容针对无状态服务：linpu-admin 可多实例部署，前面加负载均衡。

agentic 为有状态服务（持有沙箱容器与本地模型），水平扩容需配合会话粘滞。

数据层扩容：MySQL 与 PostgreSQL 采用主从复制读写分离；pgvector 数据量超过千万级向量时建议按知识库分表。

## 38 问题排查思路

排查顺序为「先看日志、再看指标、最后看数据」。

第一步，按 traceId 在应用日志中检索完整调用链。

第二步，检查容器状态与健康检查结果。

第三步，验证依赖服务连通性，包括数据库、Redis 与下游 HTTP 服务。

第四步，核对配置项与实际取值是否一致，特别注意缓存导致的配置未生效。

第五步，复现问题并抓取请求与响应原文。

## 39 灰度发布描述

发布采用三阶段灰度：先发布到 5% 的流量，观察 30 分钟；指标正常后扩大到 25%，观察 2 小时；最后全量发布。

灰度期间必须监控错误率、P95 延迟与首 Token 延迟三项指标。

任一指标恶化超过基线 20% 即回滚。

数据库变更需保证向前兼容，禁止在灰度阶段执行不可逆的 DDL。

## 40 接口鉴权方式

对外接口使用 JWT 令牌鉴权，令牌放在请求头 `Authorization` 中，格式为 `Bearer <token>`。

令牌默认有效期 30 分钟，可通过配置调整。

令牌在服务端与 Redis 中的登录会话绑定，退出登录即失效。

白名单接口不需要令牌，包括登录、注册、验证码以及对话接口 `/ai-chat`。

## 41 已知问题

已知问题一：本地向量模型首次加载需要约 8 秒，期间调用向量化接口会超时，建议预热。

已知问题二：Windows 下通过 Git 检出的 Shell 脚本带 CRLF，容器内执行会报非法选项。

已知问题三：Webpack 4 无法解析 ESM 语法依赖，markdown-it 需锁定 13.x。

已知问题四：会话表与调用记录表在同一天内被重复索引创建会报索引已存在，属历史遗留脚本缺陷。

## 42 模型输入长度上限

模型输入的上下文长度上限为 8192 tokens。

系统提示词、召回分段与历史消息共同占用该额度。

超出上限时的处理策略是从最旧的历史消息开始丢弃，而不是截断系统提示词。

召回分段单独设上限：最多 5 段、合计不超过 3000 tokens。

## 43 服务端口与协议

Nginx 监听 80 端口，协议 HTTP。

linpu-admin 监听 18080 端口，协议 HTTP，内部通过 gRPC 调用 agentic 服务。

agentic 监听 18142 端口，协议 HTTP 与 SSE。

doc-parser 监听 18143 端口，协议 HTTP。

MySQL 监听 3306，Redis 监听 6379，PostgreSQL 监听 5432，三者仅在内网可达。

## 44 成本说明

平台软件本身开源免费，不收取授权费用。

主要成本来自大模型调用，按 token 计费，一次典型问答约消耗 1500 个输入 token 与 400 个输出 token。

向量模型与 OCR 模型为本地推理，不产生调用费用，仅占用 CPU 与内存。

自建部署的服务器成本按 8 核 16 GB 规格估算。

## 45 版本改进说明

相比 v2.2，v2.4.0 有三项主要改进。

第一，文档解析模型改为懒加载，启动时间从约 4 分钟缩短到约 20 秒。

第二，模型实例增加本地缓存，避免每次对话重复构建，首 Token 延迟 P50 下降约 15%。

第三，gRPC 连接增加心跳与断线重连，长连接空闲断开后的失败率从约 3% 降到接近 0。

## 46 旧接口兼容说明

v2.4.0 保留 v2.2 的全部对外接口路径与字段名，未做破坏性变更。

新增字段一律可选，缺失时使用默认值。

已废弃字段保留至少两个大版本，并在响应中返回告警头提示迁移。

旧版客户端调用向量化接口时若不传分段参数，服务端使用默认值 500 与 50。

## 47 并发量要求

系统需支持 200 个并发在线会话。

单实例 SSE 活跃连接上限设为 300，超出后新连接排队等待，等待超时为 10 秒。

数据库连接池最大连接数 20，Redis 连接池最大连接数 8。

向量检索的并发上限为 50，超出后按队列排队。

## 48 上线前置条件

上线前必须满足五项条件。

其一，全部单元测试通过。

其二，端到端评测集准确率不低于基线，且无 P0 用例回归。

其三，数据库迁移脚本在预发环境执行成功。

其四，备份已完成并验证可恢复。

其五，监控与告警已配置并完成一次演练。

## 49 数据清洗规则

文档入库前需经过四步清洗。

第一步，去除页眉页脚与页码。

第二步，合并被换行打断的段落，保留标题层级。

第三步，把表格转换为 Markdown 表格，保留表头。

第四步，去除连续空白与不可见字符。

清洗后仍不足 20 字符的分段会被丢弃，避免产生噪声召回。

## 50 业务流程异常分支

知识库问答存在四个异常分支。

分支一：向量化未完成即发起问答，此时检索为空，走一级降级并标注「未使用知识库」。

分支二：召回分段相似度全部低于 min_score，同样走一级降级。

分支三：大模型返回工具调用但工具未挂载，捕获后返回提示并继续生成。

分支四：SSE 推送过程中连接断开，服务端在 30 秒后回收会话资源。

## 51 配置项默认值

`maxSegmentSize` 默认 500。

`maxOverlapSize` 默认 50。

`ai.embedding.batchSize` 默认 5。

`ai.agent.sessionNum` 默认 10。

`min_score` 默认 0.7，`max_result` 默认 5。

`day_lmt_per_client` 默认 1000。

## 52 健康检查方式

各服务均提供健康检查端点。

linpu-admin 的健康检查是访问根路径返回 200。

agentic 的健康检查端点为 `/health`，返回 JSON 包含状态字段。

doc-parser 的健康检查端点为 `/docs`，返回接口文档页面。

容器编排中的健康检查间隔为 30 秒，连续 3 次失败判定为不健康。

注意：若容器内未安装 curl，健康检查命令需改用其他探测方式，否则会被误判为不健康。

## 53 回滚操作步骤

回滚分三步。

第一步，把应用镜像标签切回上一个稳定版本，执行编排重建。

第二步，若涉及数据库变更，执行对应的回滚脚本；不可逆变更只能通过备份恢复。

第三步，验证健康检查与核心接口，确认错误率回到基线。

回滚全过程目标耗时不超过 15 分钟。

## 54 重试原因说明

需要重试的场景有三类。

第一类是网络抖动导致的连接重置，重试通常可以成功。

第二类是下游服务短暂不可用，配合退避重试可避免雪崩。

第三类是限流导致的拒绝，重试需带随机退避，否则会加剧拥塞。

不需要重试的场景：参数校验失败、权限不足、资源不存在，这三类属于确定性错误。

重试策略为最多 3 次，指数退避，初始间隔 200 毫秒。

## 55 幂等性说明

写接口通过 requestId 实现幂等。

客户端在请求头中携带 requestId，服务端在 Redis 中以该值为键记录处理结果，窗口期为 24 小时。

窗口期内重复提交相同 requestId 直接返回首次结果，不重复执行业务。

文件上传的幂等基于文件内容哈希，相同哈希的文件不会重复入库。

## 56 编码规范

Java 侧遵循阿里巴巴 Java 开发手册，类名大驼峰，方法名小驼峰，常量全大写。

Python 侧遵循 PEP8，函数名小写下划线，模块名小写。

单行代码长度上限 120 字符。

禁止使用裸 `except`，必须指定异常类型或至少记录完整堆栈。

禁止在业务代码中直接拼接 SQL，必须使用参数化查询。

## 57 能力边界

平台具备的能力是：基于知识库的问答、多轮会话记忆、工具调用、多智能体流程编排、文档解析与向量化。

平台不具备的能力是：模型训练与微调、实时语音交互、图像生成、视频理解。

平台不做的事：不替用户判断内容合规性，不保证大模型输出的事实正确性，不对生成内容承担法律责任。

## 58 告警处置流程

告警触发后按四步处置。

第一步，确认告警真实性，查看是否为监控误报。

第二步，判断影响范围：单实例、单服务还是全站。

第三步，执行预案：单实例问题重启容器；单服务问题走降级；全站问题启动应急响应。

第四步，恢复后补齐根因分析，24 小时内提交复盘报告。

## 60 模块启动顺序

正确的启动顺序是：

第一步，MySQL 与 Redis 先启动，MySQL 需等待健康检查通过。

第二步，PostgreSQL 启动并确认 pgvector 扩展可用。

第三步，doc-parser 启动，加载解析能力。

第四步，agentic 启动，建立与后端的 gRPC 连接。

第五步，linpu-admin 启动，执行数据库迁移并对外提供服务。

第六步，Nginx 启动，接入流量。

顺序错误的典型现象是 linpu-admin 启动时数据库迁移失败，或 agentic 长连接反复重连。
